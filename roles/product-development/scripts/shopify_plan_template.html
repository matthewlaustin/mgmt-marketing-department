Readying the catalog for Shopify

The data goes into a development store on the Ignite theme, and the theme is reshaped around the data. This page says how the working database becomes clean production data, what shape that data takes so the storefront can show it well, and which decisions are yours. Answers save in place.

The short version

  • The working tables stay as the audit trail; nothing in them is edited. A separate shop layer is built from them by a script and only that layer goes to Shopify. It carries no notes, sources, page numbers, review flags or raw text.
  • Built from a whitelist, not by deleting columns. Every field that ships is named in the build script with the rule that fills it. A test fails the build if any internal marker leaks into any exported value.
  • The data shape follows how Pentair organises its products, not how the current store does: category, product line, model, then the parts and accessories for that model. Product lines become metaobjects with their own pages; specs, facts, fitment and documents become typed metafields the theme can filter and render.
  • Ignite is the base, reshaped around that data: a product-line page with a model comparison table, a model page with its exploded parts diagram, a part page that lists every model it fits, a part-number lookup, and a document library.
  • One complete product line first, end to end in the development store, reviewed on a page like this one, then the rest in batches with a log.

What is ready today

Two layers: working data stays, a clean layer ships

You saw internal notes in Neon because mfr_catalog is the working database: it records where every value came from (URL or PDF page and the raw text), the conflicts between catalog and website, review flags and data issues. That is what makes the data defensible, so it stays, untouched. Production is a second layer built from it, and rebuilt whenever the catalog changes.

Ships schema shop

  • products: one row per SKU with exactly the Shopify product fields (handle, title, body, vendor, category, tags, price, weight, status, SEO).
  • product_lines: one row per product line, the metaobject: name, brand, category, description, features, hero images, documents, diagrams, models.
  • metafields: SKU, namespace, key, Shopify type, value. Specs, facts, cross references, replaced numbers.
  • images, files: public URLs with alt text and kind, in display order.
  • fits: part SKU to model SKU with diagram item number and quantity, both directions.

Never ships

  • Evidence, conflicts, data issues, review flags and review notes.
  • Columns named basis, source, via, raw, pages, pdf_page, title_pdf_page.
  • Internal URLs (catalog://), price notes such as CALL, photo tiers, local file paths.
  • The three service items, the one Waterco SKU, and anything not active.

Guarantee: the build names every column it copies; a test scans every exported value for these markers and for any text that is not from a manufacturer field.

The shop layer lives in SQLite beside the catalog (committed), is loaded into the Manufacturer Catalog project in Neon under its own schema, and is exported as CSV files for your eyes. Question 1 asks where you want it.

The data shape: category, product line, model, part

Pentair's catalog is already organised this way, and it is how people look for pool equipment: by what the thing is, then which line, then which model, then what fits it. The storefront gets one page type per level, each fed by its own data.

Metafields and metaobjects

Typed, with definitions created once by script, pinned in the admin, and marked filterable where Search & Discovery should use them. The theme reads them by name.

NamespaceWhatShape
specs published spec values on SKUs: voltage, horsepower, filter area, pipe size, flow, dimensions, cord length, contents, certifications...One key per attribute using Shopify's dimension, weight, number and text types with units; multi-value attributes as lists. A specs.groups JSON says which keys belong to which group and in what order, so the theme renders the spec table the same way everywhere.
factsThe derived facts: product type, sold as, installation, pump speed, pool type, surface, salt compatible, DOE rated, app controlled, voltage class, filter media, pack quantity...Short enumerated text, filterable. These drive the collection filters and the badges on product cards.

Order of work

  1. Development store accessYou create the development store with the Ignite theme installed, and a custom app on it with write access to products, files, metaobjects, metafield definitions and themes. Its token goes into the environment as SHOPIFY_SHOP and SHOPIFY_ADMIN_TOKEN, like the R2 keys; never in chat or in the repo. The theme code is pulled into the repo under theme/ so every change is versioned.
  2. Build the shop layerscripts/shop_build.py and tests. Normalises titles, handles, brands, categories, specs and units; writes the shop tables in SQLite, loads them to Neon under schema shop, writes CSV files under exports/shopify. Re-runnable whenever the catalog changes.
  3. Definitions, then one product line end to endMetaobject and metafield definitions created by script. One line (IntelliFlo3, with its models, parts, accessories, diagram and manuals) pushed through the Admin API with a dry run first.
  4. Reshape the theme around itIgnite sections and templates for the product-line page, the model page with the parts diagram, the part page with its fits list, the collection filters, the part-number lookup and the document library. Built on the one line until it reads well, with a review page for you.
  5. Full run in batchesProduct lines, products and images first, then the second pass that sets product references for fitment and parts lists, then file uploads and document links. Each batch logs created, updated and skipped SKUs with the reason.
  6. Reconcile and reportStore state read back and compared with the shop layer; differences and the SKUs still without a price or photo on one page. Moving to the live store later is the same push pointed at a different store, with the migration questions (the SKUs already on poolgeek.com, prices) asked then, not now.

The Admin API is the only route that can create metaobjects, attach files and set product references; CSV import cannot. CSV files are still produced at step 2 so you can open the data in a spreadsheet.
