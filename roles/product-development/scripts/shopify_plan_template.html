Readying the catalog for Shopify

How the working database becomes clean production data, what goes into each Shopify field, and the decisions that are yours. Answers save in place.

The short version

  • The working tables stay as the audit trail; nothing in them is edited. A new, separate shop layer is built from them by a script, and only that layer ever goes to Shopify. It carries no notes, sources, page numbers, review flags or raw text.
  • The shop layer is built from a whitelist, not by deleting columns. Every field that ships is named in the build script with the rule that fills it. A test fails the build if any internal marker leaks into any exported value.
  • Shopify's own shapes are the target: one product per SKU, Pool Geek's existing title, handle and tag conventions, typed metafields for specs and facts, product references for what fits what, Shopify Files for manuals.
  • SKUs already on poolgeek.com are enriched, not replaced: of our SKUs are already in the store. They keep their title, text, price and URL unless you say otherwise.
  • A pilot of 25 SKUs as drafts first, reviewed on a page like this one, then the full run in batches with a log you can check.

What is ready today

Two layers: working data stays, a clean layer ships

You saw internal notes in Neon because mfr_catalog is the working database: it records where every value came from (URL or PDF page and the raw text), the conflicts between catalog and website, review flags and data issues. That is what makes the data defensible, so it stays, untouched. Production is a second layer built from it.

Ships schema shop

  • products: one row per SKU with exactly the Shopify product fields (handle, title, body, vendor, type, tags, price, weight, status, SEO).
  • metafields: SKU, namespace, key, Shopify type, value. Specs, facts, cross references, replaced numbers.
  • images, files: public URLs with alt text and kind, in display order.
  • fits: part SKU to model SKU with item number and quantity, both directions.
  • store_match: our SKU against the store's product id and handle, with the update policy applied.

Never ships

  • Evidence, conflicts, data issues, review flags and review notes.
  • Columns named basis, source, via, raw, pages, pdf_page, title_pdf_page.
  • Internal URLs (catalog://), price notes such as CALL, photo tiers, local file paths.
  • The three service items, the one Waterco SKU, and anything not active.

Guarantee: the build names every column it copies; a test scans every exported value for these markers and for any text that is not from a manufacturer field.

The shop layer lives in SQLite beside the catalog (committed), is loaded into the Manufacturer Catalog project in Neon under its own schema, and is exported as CSV files for your eyes. The Neon role the app or Shopify tooling uses sees only shop. Question 1 asks where you want it.

Matching poolgeek.com

  • Matched SKUs get specs, facts, fitment, documents and photos added. Title, body, price, handle and status are left as they are. A diff report lists where the store's title or text disagrees with the manufacturer's, for you to decide one by one.
  • Store products with a Pentair, Sta-Rite or Pleatco vendor whose SKU is not in the catalog ( variants) go on a report: likely discontinued or a number Pentair now writes differently. Nothing is changed or removed in the store.
  • New SKUs are created with everything above.

Order of work

  1. Build the shop layerscripts/shop_build.py and tests. Normalizes titles, handles, brands, types, tags, specs and units; writes shop tables in SQLite, loads them to Neon under schema shop, writes CSV files under exports/shopify. Re-runnable whenever the catalog changes.
  2. Review page for the mapping and the exceptionsType and tag mapping, the 25 pilot SKUs rendered as they would appear, and the lists of SKUs lacking a price or photo.
  3. Shopify accessA custom app on poolgeek.myshopify.com with write access to products, files and metafield definitions. Its token goes into the environment as SHOPIFY_SHOP and SHOPIFY_ADMIN_TOKEN, like the R2 keys; never in chat or in the repo.
  4. Metafield definitions, then the pilotDefinitions created by script; 25 SKUs (a pump, its parts, a filter, cartridges, a light, a heater part) pushed as drafts through the Admin API with a dry run first. You check them in the admin.
  5. Full run in batchesProducts and images first, then the second pass that sets product references for fitment and parts lists, then file uploads and document links. Each batch logs created, updated and skipped SKUs with the reason.
  6. Reconcile and reportStore state read back and compared with the shop layer; differences, the unmatched store products and the SKUs still without a price or photo on one page.

The Admin API is the primary route because CSV import cannot attach PDF files, cannot set product references, and silently creates duplicates when a handle differs. CSV files are still produced at step 1 so you can open the data in a spreadsheet.
